# review-test-case — QA 测试用例评审

## 评审步骤

### 第零步：确认测试类型
收到用例后，先问用户一个问题：

> 这是 App 测试还是 Web 测试？

- 如果是 **App 测试**：第四步 App 硬规则生效，低版本升级到高版本为必查项
- 如果是 **Web 测试**：跳过第四步

### 第一步：需求覆盖检查（硬门槛）
逐条确认所有需求点是否有对应用例。有漏的直接列入问题。

### 第二步：动态维度分析
根据输入用例测的是什么功能，选择适用的测试方法判断遗漏：
- **等价类划分** — 输入项是否覆盖有效/无效等价类
- **边界值分析** — 数值/长度/数量限制是否测了边界
- **状态迁移** — 有状态变化的功能是否覆盖各转换路径
- **场景分析** — 业务流程是否覆盖主流程和异常分支
- **错误猜测** — 容易出错的地方是否有用例覆盖

根据功能特点选择最相关的方法，不强制全部使用。

### 第三步：通用专业检查项
以下维度按实际功能判断是否适用：

**防重复提交**
- 快速连续点击按钮（重复请求）
- 网络慢时用户重复操作

**Session / 登录态**
- Token 过期后继续操作的提示和跳转
- 多设备同时登录的处理

**数据展示**
- 列表为空时的空状态展示
- 列表数据量大时的分页/加载
- 超长文本输入对布局的影响

**UI 一致性**
- 深色模式下界面显示正常
- 系统字体放大后界面不错位

**安全基础**
- 敏感页面（密码/支付）截图被屏蔽
- 密码输入框内容不出现在日志里

**App 专项**
- 低版本升级到高版本，数据/功能不受影响
- 后台切回前台，数据/状态保持
- 强杀 App 重新打开，未完成操作处理正确
- 卸载重装，本地数据清除
- 权限弹窗：首次请求/拒绝后再请求
- 推送通知点击，跳转到对应页面
- 来电中断后回到 App，状态恢复正常
- 弱网/断网操作给出正确提示
- WiFi 切 4G 过程中操作不异常
- iOS 最新版 + N-1 版本兼容
- Android 主流版本兼容

### 第四步：App 硬规则（仅 App 测试）
先判断输入用例是否为 App 测试（有 iOS / Android / 移动端相关内容）。
如果是，以下必查，未覆盖则列入问题：
- 低版本升级到高版本，数据/功能不受影响

### 第五步：Japan 本地化（3 条硬规则）
每次必查，未覆盖则列入问题：
- 时区使用 JST（UTC+9）
- 价格超过 3 位数必须有千位分隔符（`1,000` 不是 `1000`）
- 设备切换日本日历 / 公历，功能不受影响

## 输出格式

分析用中文，用例内容用英文。

### 遗漏问题列表

按以下顺序排列，每条一句话说明问题和用了哪个测试方法：

1. 需求覆盖漏洞（最优先）
2. 功能/逻辑遗漏（按严重性）
3. App 硬规则遗漏（仅 App 测试，如版本升级未覆盖）
4. Japan 本地化（最后）

示例：
```
1. 未覆盖用户名为空时的提交行为（场景分析）
2. 缺少 Token 过期后继续操作的处理（错误猜测）
3. 价格未验证千位分隔符显示（Japan 本地化）
```

### 补充用例

每个遗漏对应一条用例，顺序与问题列表一致，每条最多 3 步：

| Name | Status | Test Script (Step-by-Step) - Step | Test Script (Step-by-Step) - Expected Result |
|------|--------|-----------------------------------|---------------------------------------------|
| 测试点描述 | draft | 1. step1<br>2. step2 | 1. expected1<br>2. expected2 |

规则：
- Name 直接描述测试点，不加前缀标签
- Status 一律 `draft`
- 只输出新增用例，不重复用户已提供的内容
